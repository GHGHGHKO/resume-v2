1. 문제 배경 (Problem)

1,500만 다운로드 앱 '우리동네GS'에 가입하면 택배 서비스 회원으로 자동 연계되는 통합 회원 체계를 구축해야 했습니다. 기존 택배 시스템은 단일 비회원 API 중심 구조였기 때문에, 대규모 앱 회원 트래픽이 직접 인입될 경우 기존 비회원 서비스까지 장애가 전파될 위험이 존재했습니다.

2. 분석 및 기술 검토 (Analyze)

  • Blast Radius (장애 전파 범위): 기존 비회원 서버 수정 시 비회원 접수까지 중단되는 단일 장애점(SPOF) 리스크가 있어 독립 전용 인증 서버 분리가 필수적이었습니다.
  • 보안성: HS256 대칭키 방식은 Secret Key 공유 리스크가 있어, RS256 비대칭키 및 AWS KMS 기반 공개키 서명 검증 전환이 필요했습니다.
  • 트래픽 급증: 연동 후 예상되는 급증 트래픽의 수용력을 사전에 검증해야 했습니다.

3. 해결 과정 및 실행 (Action)

  • 전용 인증/인가 서버 신규 분리: 기존 비회원 서버와 완전 격리된 독립 인증 마이크로서비스를 구축했습니다.
  • AWS KMS + RS256 비대칭키 서명: KMS 비대칭 키쌍으로 JWT를 발행하고 외부 시스템에 Public JWKS 엔드포인트를 제공하여 안전하게 서명을 검증하도록 구현했습니다.
  • Interceptor 기반 회원 식별: 택배 서비스 인입 계층에 Interceptor를 구성하여 JWT 검증 및 내부 회원 세션을 연계 생성했습니다.
  • 사전 부하 테스트: 목표 트래픽의 2배를 상정하여 k6 부하 테스트를 수행하고 Connection Pool 및 JVM GC를 최적화했습니다.

1. 문제 배경 & 분석 (Problem & Analyze)

네이버, 당근, 토스 등 주요 제휴사가 공유하는 배송조회 API에서 외부 연동사의 간헐적 지연으로 Connection Timeout이 빈발했습니다. 또한 On-Premise Redis에 의존성이 집중되어 Redis 장애 시 전체 서비스가 중단되는 SPOF 리스크가 존재했습니다.

  • 외부 클라이언트 타임아웃 세분화: 레거시 클라이언트 규격을 업그레이드하고 Connect/Read Timeout을 정밀 분리

3. 성과 (Result)

  • 외부 API Connection Timeout 문제 완전 해소 및 응답 안정성 확보
  • Redis 다운 상황에서도 DB Fallback을 통해 서비스 지속성 보장
  • 외부 API 호출량 획기적 절감으로 외부 시스템 의존 리스크 최소화

💡 핵심 엔지니어링 챌린지 및 해결 과정

🎯 챌린지 1: Spring WebFlux & Reactive Redis 기반 실시간 위치 중계 (socket 모듈)

[문제점] 수많은 러너와 관전자가 1초 주기로 위치 데이터를 주고받는 환경에서, 전통적인 Spring MVC (Thread-per-request) 방식은 동시 접속자 증가 시 스레드 풀 고갈 및 컨텍스트 스위칭 오버헤드가 극심했습니다.

[해결책]

  • Spring WebFlux 도입: Netty 기반 Non-blocking Event Loop 모델을 채택하여 최소한의 스레드로 수천 개의 동시 WebSocket 커넥션을 유지하도록 전용 WebSocket 서비스(pulse.runmarket.cc)로 분리했습니다.
  • Reactive Redis Pub/Sub 채널링: 방(Room) 단위 고유 채널을 생성하고 Redis Reactive Subscriber를 활용해 분산 노드 간 지연 없는 실시간 브로드캐스팅을 구현했습니다.
  • 메모리 계층화: 실시간 위치는 Redis In-Memory에 TTL과 함께 유지하고, 러닝 종료 시점에만 PostgreSQL로 영속화하여 DB I/O 부하를 원천 차단했습니다.

🎯 챌린지 2: Google Jib 기반 데몬리스 컨테이너 빌드 & Helm Chart 선언적 IaC 배포

[문제점] 멀티모듈(web, socket, batch) 애플리케이션 빌드 시 Docker 데몬 종속성으로 인해 CI 환경이 무거워지고, 수동 리소스 관리 시 환경 불일치와 휴먼 에러 위험이 있었습니다.

[해결책]

  • Google Jib 빌드 파이프라인: Docker 데몬 없이 Gradle 플러그인(Jib)을 통해 OCI 표준 컨테이너 이미지를 레이어별로 최적화하여 빌드(gudrb963/runmarket-pacer, gudrb963/runmarket-pacer-socket). 레이어 캐싱으로 CI 빌드 속도를 극대화했습니다.
  • Helm Chart 템플릿화: helm/runmarket 차트를 작성하여 Deployment, Service, Ingress, ConfigMap을 코드화(IaC)했습니다.
  • 무중단 롤링 업데이트: readinessProbe, livenessProbe를 정밀하게 구성하여 배포 중 커넥션 유실 없는 무중단 업데이트를 달성했습니다.

🔬 워커 노드 선정 Trade-off: AWS Fargate vs EC2 노드그룹

MWAA KubernetesPodOperator 실행 환경으로 Fargate와 EC2 노드그룹을 벤치마크 테스트했습니다.

  • AWS Fargate: Pod 프로비저닝 시간(45~90초) + Java 런타임 기동 시간으로 인해 짧은 주기의 배치 실행 시 큐 적체 발생
  • EC2 Warm NodeGroup: 노드 사전 프로비저닝 및 Docker 이미지 캐싱으로 Pod 기동 시간 3초 이내 보장
  • 결과: EC2 관리형 노드그룹 채택 + 스팟 인스턴스 정책 혼합으로 기동 지연 해소 및 인프라 비용 30% 절감 달성
