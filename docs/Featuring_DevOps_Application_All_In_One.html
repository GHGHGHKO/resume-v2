IDC → AWS 배치·서비스 이관 (팀 공동 작업)

기간: 사전 쿼리 분석·점진적 수정 2023.01–2023.05, 본 이관 2023.06–2024.03, 안정화 2024.04까지. 내부 3명과 필요한 기간 참여한 외주 3명이 협력했습니다.

문제와 본인 역할

  • 외주 구축 IDC 배치의 유지보수·배포가 어려웠고, 서로 다른 테이블 구조의 PPAS DB 2종 사이에 양방향 데이터 흐름과 락 문제가 있었습니다.
  • 본인은 Airflow 설계·이관, DAG 정비·배포 자동화, Core API·Spring Batch SQL 전환, 순차 운영 배포와 외주 인력 온보딩을 담당했습니다. 13개 서비스 이관은 팀 공동 성과입니다.

단계적 전환과 복귀

  • SQL을 변경한 동일 Spring Batch 이미지를 IDC·AWS 양쪽 레지스트리에 배포하고, IDC 동작 및 실행 Pod 종료를 확인한 뒤 DAG를 순차 전환했습니다. 문제가 생기면 IDC DAG를 다시 켤 수 있도록 했습니다.
  • 기존·변경 쿼리의 결과를 동기화된 IDC·AWS DB에서 비교했습니다. 모든 쿼리 누락을 자동 검출하는 체계는 아니었으며, 전환 뒤 누락된 SQL 문법 오류는 긴급 수정·테스트 후 배포한 사례가 있습니다.

MWAA 운영 구조와 결과

  • MWAA의 KubernetesPodOperator가 EKS에서 Spring Batch 컨테이너를 실행하도록 구성했습니다. DAG 커밋 → CI/CD → S3 Sync와 Airflow Variables API를 통한 이미지 버전 갱신 흐름을 구축했습니다.
  • 미사용 DAG를 제거하고 저처리량 제휴사 20곳의 전송 작업을 병렬 Flow로 통합해 DAG를 약 250개에서 170개로 줄였습니다.
  • 5분 주기 배치에서 Fargate 준비 시간 약 200초와 EC2 약 80초를 비교해 EC2 실행 환경을 선택했습니다. 약 60% 단축은 준비 시간에 한정되며 전체 Job 처리 시간·운영 비용 절감률이 아닙니다.
  • 기존의 실패 지점 재개 구조를 활용해 Job 재시도와 SNS 알림을 구성했습니다. 재시도는 DB 락의 근본 원인 해결과 구분합니다.

우리동네GS 택배 인증·인가 서버 (blackpink)

  • Java 21과 Spring Security, AWS KMS를 사용해 stateless 토큰의 발급·검증·갱신과 권한 규칙을 설계·구현했습니다.
  • GRM 발급 토큰 검증과 회원 식별을 담당했습니다. 실제 회원 계정 연결 API는 다른 담당자가 구현했습니다.
  • 현장 장비 약 18,000대의 인증과 키오스크 게스트 인증을 구현했습니다. 그 외 주요 업무 서비스는 Java 11을 사용했습니다.

GRM 통합회원 플랫폼 출시 후 개선

2025.10부터 참여했습니다. 2024년 초기 구축이나 데이터 이관을 본인 기여로 기재하지 않습니다.

  • OTP 우회와 타 계정 정보 접근 등 인증·인가 취약점을 수정하고, 회원 정책·CI 암호화 경로를 개선했습니다.
  • 중복 요청 파라미터 로그 155건을 정리했습니다. 트래픽 보정 배포 전후 비교에서 본인 담당 변경분의 적재량은 약 43.5GB/일, 팀 1차 배포 기준 전체 감소량은 약 87GB/일(40.7%)입니다.
