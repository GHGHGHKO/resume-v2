### [프로젝트 1] 택배 서비스 IDC → AWS 클라우드 이관 및 MWAA 최적화
- **기간:** 2023.01 – 2023.10 (10개월)
- **역할:** 인프라 마이그레이션 리드, MWAA 파이프라인 설계 및 배치 자동화
- **규모:** 13개 서비스, 이기종 DB 2개, 일 평균 1,280만 req(피크 82만 req/h), Airflow 250 DAGs
- **기술 스택:** AWS (EKS, EC2, MWAA, RDS, S3), Apache Airflow, PostgreSQL, Docker, GitHub Actions, ANSI SQL

#### 1. 문제 배경 (Problem)
IDC 기반 온프레미스 택배 레거시 시스템을 AWS로 전환해야 하는 상황에서, 벤더 종속 DB(EDB) 쿼리로 인해 AWS DMS 자동 마이그레이션이 불가능했습니다. 또한 외주 개발사에서 구축한 250여 개의 Airflow DAG가 높은 결합도와 비효율적인 스케줄링으로 운영되고 있어 잦은 지연과 장애가 발생했습니다.

#### 2. 원인 분석 및 기술 검토 (Analyze)
- **DB 전환:** EDB 전용 문법과 저장 프로시저가 광범위하게 산재되어 표준 SQL 전환이 필수적이었습니다.
- **워커 노드 지연:** MWAA KubernetesPodOperator 워커로 Fargate 검토 시, Java 앱의 콜드스타트와 Fargate 프로비저닝 지연으로 인해 Pod 기동에 수십 초~수 분이 소요되어 스케줄 지연이 심화됨을 확인했습니다.
- **운영 복잡도:** 외주 의존도로 인해 장애 발생 시 즉각적인 원인 파악 및 수정 배포가 불가능했습니다.

#### 3. 해결 과정 및 실행 (Action)
- **EDB 종속 쿼리 ANSI SQL 전수 표준화:** 외주 협업을 통해 13개 서비스의 EDB 전용 SQL을 PostgreSQL 호환 ANSI SQL로 변환하고 테스트 파이프라인을 구축하여 무결성을 검증했습니다.
- **AWS MWAA 직접 구축 및 아키텍처 재설계:** IDC Airflow를 AWS MWAA 환경으로 직접 마이그레이션하고, Fargate vs EC2 노드그룹 벤치마크 테스트를 거쳐 기동 속도가 빠른 EC2 노드그룹을 채택했습니다.
- **DAG 통폐합 및 리팩토링:** 250개의 DAG 중 중복·미사용 DAG 80개를 정리하고, 스케줄링 주기를 재배치하여 170개로 최적화했습니다.
- **CI/CD 배포 자동화 구축:** GitHub Actions와 S3 Sync 파이프라인을 구축하여 DAG 코드 수정 시 즉시 검증 및 배포/롤백이 가능한 환경을 구현했습니다.

#### 4. 엔지니어링 성과 (Result)
- **인프라 비용 30% 절감:** DAG 통폐합(250개 → 170개) 및 인스턴스 효율화로 클라우드 운영 비용 30% 절감 달성
- **배치 기동 지연 해소:** EC2 워커 노드 채택으로 Pod 기동 지연을 최소화하여 정시 배치 완료율 99.9% 달성
- **사내 직접 운영 체계 완비:** 외주 의존도를 100% 제거하고 코드 레벨에서 기민하게 유지보수할 수 있는 내부 역량 확보

### [프로젝트 2] 우리동네GS × 택배 회원 연동 전용 인증 서버 구축
- **기간:** 2024.01 – 2024.06 (6개월)
- **역할:** 인증/인가 아키텍처 설계, 백엔드 서버 구축 및 트래픽 부하 테스트 리드
- **규모:** 1,500만 다운로드 앱 '우리동네GS', 월 1,197만 req, 피크 트래픽 37,654 req/h
- **기술 스택:** Java, Spring Boot, AWS KMS, JWT (RS256), Kubernetes (EKS), Docker, nGrinder/k6

#### 1. 문제 배경 (Problem)
1,500만 다운로드의 대표 앱 '우리동네GS'에 가입한 유저가 별도 가입 절차 없이 택배 서비스를 이용할 수 있도록 통합 회원 체계를 구축해야 했습니다. 기존 택배 시스템은 단일 비회원 API 중심 구조였기 때문에, 대규모 앱 회원 트래픽이 직접 인입될 경우 기존 비회원 서비스까지 장애가 전파될 위험이 컸습니다.

#### 2. 원인 분석 및 기술 검토 (Analyze)
- **Blast Radius (장애 전파 범위):** 기존 비회원 API 서버에 회원 로직을 직접 통합할 경우 코드 복잡도가 증가하고, 장애 시 비회원 택배 접수까지 중단되는 단일 장애점(SPOF) 리스크가 존재했습니다.
- **인증 토큰 보안:** 기존 HS256 대칭키 방식은 secret key를 외부 시스템과 공유해야 하므로 보안에 취약했습니다. 비대칭키(RS256) 기반 서명 및 공개키 검증 체계가 필수적이었습니다.
- **트래픽 급증:** 앱 연동 시 수배 이상의 트래픽 폭증이 예상되므로 실환경 기반의 사전 부하 검증이 선행되어야 했습니다.

#### 3. 해결 과정 및 실행 (Action)
- **전용 인증/인가 서버 신규 분리:** 기존 비회원 서비스와 격리된 독립 인증 마이크로서비스를 구축하여 장애 전파 범위를 원천 차단했습니다.
- **AWS KMS + RS256 비대칭키 서명 도입:** AWS KMS의 비대칭 키쌍을 활용하여 인증 서버가 토큰을 발행하고, 외부에 Public JWKS 엔드포인트를 제공하여 안전하게 서명을 검증할 수 있도록 설계했습니다.
- **Interceptor 기반 회원 연계:** 택배 웹/API 인입 계층에 Interceptor를 구성하여 JWT 검증 및 내부 회원 식별, 세션 자동 생성을 매끄럽게 처리했습니다.
- **부하 테스트 및 JVM 최적화:** 예상 피크 트래픽의 2배를 목표로 k6/nGrinder 부하 테스트를 수행하고, Connection Pool 및 HikariCP, JVM GC 튜닝을 선행했습니다.

#### 4. 엔지니어링 성과 (Result)
- **트래픽 8.5배 성장 안정적 수용:** 서비스 오픈 후 월 요청량이 140만 건에서 1,197만 건으로 8.5배 급증했으나 안정적으로 수용
- **피크 에러율 0.042% 유지:** 피크 37,654 req/h 트래픽 인입 상황에서도 0.042%의 극저 에러율 유지
- **독립 격리 아키텍처 완성:** 비회원 서비스 영향도 Zero(0)를 달성하며 안전한 통합 회원 환경 구현

### [프로젝트 3] GS리테일 차세대 CRM 서비스 안정화 & CI/CD 최적화
- **기간:** 2022.10 – 2023.03 (6개월)
- **역할:** API 보안 취약점 패치, 대용량 배치 쿼리 튜닝, Dockerfile CI/CD 빌드 최적화
- **기술 스택:** Java, Spring Boot, Spring Batch, PostgreSQL, Docker, GitHub Actions, Datadog

#### 1. 문제 배경 (Problem)
빅뱅 오픈 직후 CRM 서비스에서 계정 탈취가 가능한 API 보안 취약점이 발견되었고, 법정대리인 데이터 파기 배치에서 중복 키 충돌로 야간 배치가 실패했습니다. 또한 프론트엔드/백엔드 배포 파이프라인의 빌드 시간이 20분 이상 소요되어 긴급 핫픽스 배포에 큰 병목이 발생했습니다.

#### 2. 원인 분석 및 해결 과정 (Analyze & Action)
- **보안 취약점 패치:** 비밀번호 변경 API가 OTP 인증 완료 여부 세션 상태를 검증하지 않는 취약점을 분석하고, 단계별 토큰 검증 및 계정 일치 로직을 추가하여 패킷 조작을 통한 계정 탈취를 원천 차단했습니다.
- **배치 및 쿼리 최적화:**
  - 법정대리인 파기 배치의 SQL WHERE 조건에 삭제 예정일자(`del_schd_dt`) 누락을 확인하고 조건을 보완했으며, 메모리 내 `HashSet`을 활용해 중복 데이터 처리를 방어했습니다.
  - Correlated EXISTS 서브쿼리로 인해 Full Table Scan이 발생하는 병목 쿼리를 INNER JOIN으로 전환하여 실행시간을 1초에서 200ms로 80% 단축시켰습니다.
- **Dockerfile 빌드 파이프라인 개선:**
  - Dockerfile 내 `COPY . .`로 인해 `node_modules` 및 불필요한 파일 전체가 컨텍스트로 전송되던 구조를 파악했습니다.
  - 빌드 아티팩트(.zip)만 선별 복사하도록 Multi-stage Build 구조로 개선하여 빌드 소요시간을 20분에서 2분으로 단축시켰습니다.

#### 3. 엔지니어링 성과 (Result)
- 보안 취약점 원천 패치로 금융/개인정보 수준의 보안성 확보
- 핵심 CRM 쿼리 레이턴시 80% 개선 (1s → 200ms)
- CI/CD 빌드 및 배포 시간 90% 단축 (20분 → 2분)으로 개발 생산성 및 장애 대응 기민성 극대화

### [프로젝트 4] 대외 제휴 배송조회 API 고가용성 & 다계층 캐시 레이어 구축
- **기간:** 2021.11 – 2022.06 (8개월)
- **역할:** 캐시 레이어 설계 및 장애 격리(Fallback) 패턴 구현
- **규모:** 네이버, 당근, 토스 등 주요 제휴사 공유 공용 API
- **기술 스택:** Java, Spring Boot, Redis, PostgreSQL, Spring Retry

#### 1. 문제 배경 & 분석 (Problem & Analyze)
대외 제휴사가 공유하는 배송조회 API에서 외부 연동사의 간헐적 응답 지연으로 인해 Connection Timeout이 빈발했습니다. 또한 On-Premise Redis에 인증 토큰과 조회 데이터가 전적으로 의존되어 있어 Redis 다운 시 전체 배송조회 서비스가 중단되는 SPOF 구조였습니다.

#### 2. 해결 과정 (Action)
- **Dynamic TTL 기반 캐싱:** 배송 상태(배송준비/배송중/배송완료)에 따라 캐시 유효기간(TTL)을 차등 적용하여 불필요한 외부 API 반복 호출을 차단했습니다.
- **다계층 캐시 & DB Fallback 구현:** 인증 토큰 및 배송 데이터를 DB + Redis Layered Cache로 관리하고, Spring Retry / `@Recover` 패턴을 적용하여 Redis 장애 발생 시 자동으로 DB Fallback으로 전환되도록 설계했습니다.
- **외부 연동 클라이언트 개선:** 레거시 연동 라이브러리를 최신 규격으로 업그레이드하고 Connect/Read Timeout을 세분화하여 스레드 풀 고갈을 방지했습니다.

#### 3. 엔지니어링 성과 (Result)
- 외부 연동사 지연으로 인한 Connection Timeout 완전 해소
- Redis 장애 상황에서도 서비스 중단 없이 DB Fallback으로 지속 가용성 확보
- 외부 API 호출량 획기적 절감 및 시스템 리소스 효율화
