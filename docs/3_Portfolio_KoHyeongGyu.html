💡 핵심 엔지니어링 챌린지 및 해결 과정

🎯 챌린지 1: 실시간 대규모 위치 브로드캐스팅 성능 최적화

[문제점] 수많은 러너와 관전자가 1초 주기로 위치 데이터를 주고받는 환경에서, 전통적인 Spring MVC (Thread-per-request) 방식은 동시 접속자 증가 시 스레드 풀 고갈 및 컨텍스트 스위칭 오버헤드가 극심했습니다.

[해결책]

  • Spring WebFlux 도입: Netty 기반 Non-blocking Event Loop 모델을 채택하여 최소한의 스레드로 수천 개의 동시 WebSocket 커넥션을 유지하도록 전환했습니다.
  • Reactive Redis Pub/Sub 채널링: 방(Room) 단위 고유 채널을 생성하고 Redis Reactive Subscriber를 활용해 분산 노드 간 지연 없는 실시간 브로드캐스팅을 구현했습니다.
  • 메모리 계층화: 실시간 위치는 Redis In-Memory에 TTL과 함께 유지하고, 러닝 종료 시점에만 PostgreSQL로 영속화하여 DB I/O 부하를 원천 차단했습니다.

🎯 챌린지 2: Kubernetes(K3s) & Helm Chart 기반 선언적 IaC 배포

[문제점] 멀티모듈(API, WebSocket, Batch) 애플리케이션의 설정과 리소스를 수동 관리할 경우 환경 불일치와 휴먼 에러 위험이 컸습니다.

[해결책]

  • Helm Chart 템플릿화: 공통 인프라 템플릿을 Helm Chart로 정의하고 values-dev.yaml, values-prod.yaml로 환경별 설정을 코드화(IaC)했습니다.
  • 무중단 롤링 업데이트: readinessProbe, livenessProbe를 정밀하게 구성하여 배포 중 커넥션 유실 없는 무중단 업데이트를 달성했습니다.
  • GitHub Actions 자동화: 코드 푸시 시 Docker Multi-stage 빌드 → 레지스트리 푸시 → Helm 업그레이드로 이어지는 전자동 CI/CD를 구축했습니다.

🔬 워커 노드 선정 Trade-off: AWS Fargate vs EC2 노드그룹

MWAA KubernetesPodOperator 실행 환경으로 Fargate와 EC2 노드그룹을 벤치마크 테스트했습니다.

  • AWS Fargate: Pod 프로비저닝 시간(45~90초) + Java 런타임 기동 시간으로 인해 짧은 주기의 배치 실행 시 큐 적체 발생
  • EC2 Warm NodeGroup: 노드 사전 프로비저닝 및 Docker 이미지 캐싱으로 Pod 기동 시간 3초 이내 보장
  • 결과: EC2 관리형 노드그룹 채택 + 스팟 인스턴스 정책 혼합으로 기동 지연 해소 및 인프라 비용 30% 절감 달성
